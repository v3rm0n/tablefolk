Technical walkthrough

How does a P2P
card game work?

Sasku uses Nostr relays to set up WebRTC connections. The four browsers then exchange signed game records, jointly shuffle an encrypted deck, open private hands, and audit every play.

01 / Connection

First, the browsers find each other.

A relay introduces the players. Once the links are ready, the four browsers exchange game messages directly.

✓

Now the table is connected. Game actions travel between the browsers over authenticated peer links. The relay’s job was the introduction.

Some networks block browser-to-browser links. This build has no TURN fallback, so a table cannot start if those links fail.

Protocol trace / connection

From invitation to a ready peer.

These checks establish identity and catch up history before anyone makes a new move.

g · h · r · s Invitation fragment
The URL fragment names the 16-byte game ID, the host’s Ed25519 public key, and the rules and signaling profiles. The host key is the first identity to trust. URL fragments are not sent with the page’s HTTP request.
SDP / ICE Signaling
Browsers exchange WebRTC offers, answers, and ICE candidates through Nostr relay WebSockets. A room-derived AES-GCM key encrypts this traffic, but does not prove a player’s identity; the later HELLO does. STUN helps find reachable addresses; this build has no TURN relay.
HELLO Peer authentication
After a WebRTC data channel opens, each side signs a message binding its Ed25519 identity, this game ID, and both observed DTLS certificate fingerprints. Application messages remain blocked until both directions pass.
ROSTER / READY Table agreement
The host signs the four-seat roster and the rules hash. Every player signs readiness for that exact roster hash, so a peer cannot quietly change the players or first-round rules.
seq / prev History and catch-up
Every durable record uses canonical CBOR and an Ed25519 signature, with its author’s sequence number and previous hash. Peers replay the original bytes, reject gaps or conflicts, and acknowledge an exact history prefix only after saving and validating it. New actions wait for all three peers to catch up.

Protocol trace / round

What each signed message does.

The same record is checked independently by all four browsers.

KEY_SHARE Joint encryption key
Each seat publishes a public key share with a proof that it knows the matching secret. The shares form one public deck key; no browser has the whole private key. The four players also commit and reveal a seed, while this first-round profile fixes the dealer and deal order.
SHUFFLE Verified mixing
The 36 known cards become encrypted positions. Each seat permutes and re-encrypts the deck in turn, then publishes a candidate Bayer–Groth shuffle proof. Peers verify it in a temporary WASM worker before accepting the next shuffle.
SHARES Private deal
Each seat receives nine encrypted positions. The three non-owners publish proven decryption shares for those positions. Only the owner combines them with its own secret share to learn the cards; its game key is saved locally so the hand can be rebuilt after a reload.
ACTION Bids, trump, and plays
A signed action records each turn. A play includes the owner’s missing decryption share and proof, so everyone can open that one card and verify the public trick. Whether an earlier player illegally failed to follow suit cannot be known until their whole hand is open.
AUDIT_DISCLOSE Final replay
Once all 36 cards have been played, each seat signs a final participation marker. The markers disclose no additional cards in this one-round game. Each browser reconstructs the original hands, replays the action history, and computes a valid score or a specific violation locally.

The privacy boundary

Your unplayed cards stay in your browser.

The public record includes the roster, bids, trump, proofs, played cards, and scores. Those clues can narrow what another player might hold, but they do not reveal the unplayed cards themselves.

♠Only you can open

✓Everyone can verify

The public actions, opened cards, and shuffle proofs.

Current build

One experimental round.

All four players must stay connected. On reload, a browser rechecks saved signatures and shuffle proofs before rebuilding its hand from its local key. The one-tab demo uses local message delivery in place of WebRTC; the game steps are the same.

The shuffle proof backend still awaits independent review. Privacy assumes working cryptography, at least one honest shuffler, and private local keys. A player can also stall the game by withholding messages or disconnecting.
